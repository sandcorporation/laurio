# 세무 — 소득세법

> 법률 자문이 아니다. 벤더에게 확인받은 것은 그렇게 표시했다. 색인은 [README.md](README.md).

## 공모전 상금은 기타소득이다

국세청 기준으로 공모전 상금은 **기타소득**이고 필요경비 80% 가 인정된다. 그래서
원천징수는 지급액의 **4.4%** 다 — 소득세 20% + 지방소득세(소득세의 10%) = 22% 를
과세 대상 20% 에 적용한 값이다. 필요경비가 60% 로 인정되는 경우의 8.8% 와, 사업소득
세율 3.3% 는 이 서비스가 적용하는 값이 **아니다**
(`backend/tests/test_payouts.py` 가 이 셋을 구분해 고정한다).

## 원천징수와 지급명세서는 Codemit 가 진다 — 벤더 확인됨

토스페이먼츠 지급대행은 오픈마켓 셀러 정산(사업소득·매출)을 상정한 서비스라 공개
문서에 기타소득 원천징수 대행의 근거가 없었고, [ADR-0008](../adr/0008-toss-handles-identity-laurio-handles-tax.md) 은
「세무는 Codemit 책임으로 가정하고 설계한다」고 적었다. 그 뒤 **토스페이먼츠와
포트원 양쪽에 물어 같은 답을 받았다** — 지급대행사는 우리가 뗀 뒤의 금액을 이체할
뿐이다. 원천징수의무자도, 지급명세서 제출 주체도 Codemit 다.

포트원 마케팅에 「원천징수 자동 계산」이 적혀 있으나 담당자 답변과 어긋난다 — 입점
셀러 정산(사업소득)용 기능이다. **마케팅 문구를 근거로 이 결정을 뒤집지 마라**
(ADR-0008).

이 확인이 두 가지의 근거다:

- **주민등록번호를 우리가 받는다.** 지급명세서에 필요하다. 가입 시점이 아니라
  **Payout 이 확정된 시점에만** 수집하고, 다른 어떤 테이블과도 섞이지 않는 별도
  암호화 테이블에 둔다(`backend/payouts/models.py` `TaxIdentity`). 그래서 「지급
  확정 · 신원 대기」(`Payout.Status.CONFIRMED_IDENTITY_PENDING`)가 정식 상태로
  존재하고, 그동안 금액은 원장에 개발자 미지급금으로 남아 사라지지 않는다.
- **원천징수 예수금은 별도 계정이다.** 국세청에 낼 남의 돈이라 플랫폼 수익과 섞지
  않는다(`backend/ledger/models.py` `Account.WITHHOLDING_TAX_PAYABLE`,
  [ADR-0004](../adr/0004-double-entry-ledger.md)).

## 계산 — 값은 `PlatformPolicy` 에, 규칙은 `payouts.services` 에

요율은 코드 상수도 환경변수도 아니고 DB 의 단일 행 `PlatformPolicy` 에 살며 운영자
API 로만 바뀐다([ADR-0023](../adr/0023-policy-values-live-in-the-database-and-change-only-through-the-operator-api.md)).
기본값(`backend/policies/models.py`):

| 필드 | 기본값 | 뜻 |
| --- | --- | --- |
| `platform_fee_bps` | 1000 | 플랫폼 수수료 10% |
| `withholding_tax_bps` | 440 | 원천징수 4.4% |
| `withholding_necessary_expense_bps` | 8000 | 필요경비 80% |
| `withholding_minor_income_exempt_won` | 50,000 | 과세최저한 — 기타소득금액 5만원 이하 |

`backend/payouts/services.py` `_compute_amounts` 가 이 행 하나에서 수수료·원천징수·
실지급액을 낸다. 세 가지 규율이 걸려 있다:

- **과세최저한.** 기타소득금액(지급액 × (1 − 필요경비율))이 5만원 이하면 원천징수가
  없다 — 지급액 기준 **250,000원 이하**다. 이 임계값은 필요경비율과 과세최저한에서만
  유도되고 **원천징수율과는 독립**이다(`_withholding_exempt_threshold`). 누가
  원천징수율만 3.3% 로 잘못 되돌려도 면제 경계가 조용히 따라 움직이지 않는다.
- **적용 요율 스냅샷.** 요율이 바뀔 수 있으므로 「이 지급은 왜 이만큼 뗐는가」에 답할
  수 있게 Payout 이 적용된 요율을 남긴다. 면제된 지급은 명목 요율이 아니라 **0** 을
  남긴다 — 「4.4% 를 적용했다」는 기록과 「0원 뗐다」는 금액이 모순되면 이 스냅샷으로
  만든 지급명세서가 뗀 적 없는 세금을 보고하게 된다.
- **단수가 사라지지 않는다.** 수수료와 원천징수는 내림, 실지급액이 나머지 전부를
  가져간다. `platform_fee_bps + withholding_tax_bps <= 10000` 을 CheckConstraint 가
  강제해 실지급액이 음수가 될 수 없다.

## 열린 항목

4. **사업소득 재분류.** Developer 가 반복적·직업적으로 참가하면 기타소득이 아니라
   사업소득(3.3%)으로 볼 여지가 있다([REQUEST.md](../../REQUEST.md) 「세금」). 어느
   빈도부터 그런지, 그때 누가 어떻게 판단하는지가 정해지지 않았다. 세무 검토 사항.
5. **지급명세서 기능이 없다.** 제출 주체가 Codemit 인 것은 확인됐지만, `TaxIdentity`
   와 Payout 스냅샷에서 명세서를 만들어 제출하는 경로는 저장소에 없다. 요율 스냅샷과
   면제 시 0 기록은 이 기능을 위한 준비다.
6. **부가세.** 플랫폼 수수료(Developer 공제)와 개최비(Sponsor 결제)는 Codemit 의
   매출이라 부가세·세금계산서·현금영수증 처리가 따르는데, REQUEST.md 도 코드도 이
   문제를 다루지 않는다. Sponsor 가 법인이면 상금의 비용 처리 서류도 필요하다.
