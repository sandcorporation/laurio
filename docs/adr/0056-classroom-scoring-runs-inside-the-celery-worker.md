# 강의실 채점은 Celery 워커 안에서 돈다 — 「진입점은 내부 HTTP 하나」의 예외

Status: Amended by ADR-0059 (2026-10-06 결정)

ADR-0003 의 스캔은 진입점이 내부 인증 HTTP 하나다(`core.tasks`). beat·수동 curl·워커가 모두
같은 경로를 거쳐야 「두 번 쏴도 한 번만 통과한다」를 지키는 코드가 하나로 남는다. 강의실 즉시
채점(#378)도 그 모양을 따랐다. 태스크가 `/api/internal/classroom/attempts/{id}/score` 를
`call_internal`(30초)로 부르고, 채점은 그 요청을 받은 gunicorn 워커 안에서 돌았다.

그 요청에는 30초 예산이 있다. 호출부가 30초를 기다리고, gunicorn 은 `--timeout` 기본값
30초에 워커를 죽인다. 그런데 강의실 채점은 강사의 키로 추론 모델(gpt-5 계열)을 부르고, 그
응답은 30초를 자주 넘긴다(#402 는 그래서 벤더 타임아웃을 120초로 잡았다). prod 에서 벤더가
늦자 워커가 채점 도중 죽었다(GlitchTip 오류 87, #581). 시도 기록이 남지 않아 실패 한도에
닿지 않았고, 재시도와 매 tick 의 스캔이 벤더를 다시 불러 강사 키의 비용만 나갔다. #581 은
벤더 타임아웃을 20초로 줄여 막았다. 추론 모델의 정상 응답도 실패로 치는 값이다.

**강의실 채점은 Celery 태스크 `classroom.score_attempt` 하나로만 돌고(#582), 그 태스크가 워커
안에서 직접 채점한다.** 내부 엔드포인트는 지웠다. 선례는 `core.backup_database` 다 —
30초를 넘길 수 있는 일은 워커 안에서 돈다.

- **두 길은 큐에 넣기만 한다.** 제출이 커밋되면 즉시 채점으로 한 번, 60초 안전망 스캔
  (`classroom-submission-scoring`)이 아직 채점되지 않은 시도마다 한 번. 스캔 자체는 여전히
  ADR-0003 의 내부 HTTP 경로로 돈다. 스캔 요청이 채점을 하지 않으므로 「스캔 한 요청이
  50건을 이어 채점해 30초를 넘는다」도 함께 사라진다.
- **「두 번 쏴도 한 번만」은 행 잠금이 지킨다.** `_score_one` 의
  `select_for_update(skip_locked=True)` 와 「이미 채점됨」 확인이다. HTTP 경로가 지키던 것도
  사실 이 잠금이었다(#377 AC14). 같은 시도의 태스크가 둘 돌아도 벤더는 한 번 불린다.
- **중복 큐는 「큐에 넣은 시각」(`ClassroomSubmission.scoring_queued_at`)이 막는다.** 넣는
  자리(`classroom.scoring.enqueue_scoring`)가 조건부 UPDATE 로 그 시각을 찍고, 이긴 쪽만
  `.delay()` 한다. 그 시각이 5분 안이면 스캔이 다시 넣지 않는다. 태스크는 처리를 마치면(채점·
  실패 기록·건너뜀) 그 시각을 비운다 — 실패한 시도는 다음 tick 에 다시 들어간다(전과 같은
  간격). 워커가 죽어 잃은 태스크는 5분 뒤 다시 줍힌다. 발행이 실패하면 찍은 시각을 되돌린다.
- **시간은 바깥으로 갈수록 길다.** 벤더 180초 < soft 한도 210초 < hard 한도 240초 < 큐 창
  5분. soft 한도는 채점 도중 예외를 던지고 `_score_one` 이 그것을 실패한 시도로 남긴다 —
  실패 한도(5회)에 닿는다. hard 한도는 프로세스를 죽인다. 그 경우만 기록 없이 남고, 큐 창이
  지나면 다시 줍힌다. 180초는 300KB 소스를 추론 모델(높은 추론 강도)이 읽는 응답도 담는 값이다.
- **Celery 재시도는 없다.** 실패는 시도 기록으로 남고 스캔이 다시 넣는다. 둘이 함께 다시
  부르면 실패 한도를 두 배로 빨리 쓴다.
- **채점은 전용 워커가 한다.** 배포 compose 에 `celery-scoring`(같은 이미지, `-Q
  classroom-scoring`, prefork 동시성 8, 미리 가져오기 1, 메모리 약 1GB)을 두고, 기존
  `celery-worker` 는 `-Q celery` 로 그 큐를 소비하지 않는다. 3분 걸리는 채점이 60초 스캔
  태스크를 막지 않는다. 채점 워커만 `stop_grace_period: 4m` 이다 — 따뜻한 종료로 채점 중인
  것을 마저 끝낸다. `deploy.sh` 는 이 서비스를 맨 끝에 바꾸고, 내리고 올리는 배포에서는 먼저
  따로 내린다.
- **dev·CI 는 `CELERY_TASK_ALWAYS_EAGER` 다.** 큐에 넣는 자리에서 태스크가 그대로 돈다(흉내
  어댑터라 빠르다). 그래서 채점 경로가 환경마다 갈리지 않는다 — 전에는 dev·CI 에서 즉시 채점
  태스크가 돌지 않고 스캔이 직접 채점했다. 배포 환경은 그 값이 켜지면 부팅을 거부한다(켜지면
  채점이 다시 요청 안에서 돈다). dev 의 `--profile celery` worker·beat 는 그 값을 끈다.

## 고려한 대안

- **벤더 타임아웃 20초를 그대로 둔다(#581).** 추론 모델·높은 추론 강도에서 정상 응답도
  실패로 남고 5회 뒤 플랫폼 미달이 된다. #402 의 「추론 모델엔 넉넉히」를 포기한다.
- **강의실 채점 경로의 예산만 늘린다** — `call_internal` 타임아웃과 gunicorn `--timeout` 을
  2분 넘게. gunicorn 의 timeout 은 모든 요청의 「멈춘 워커」 감지를 늦추고, 워커 넷 중 하나가
  2분 묶이는 일이 정상이 된다. 스캔은 배치를 이어 처리하므로 한 요청이 `배치 × 2분` 까지
  길어진다. 배포의 겹쳐 바꾸기에서 옛 backend 가 받던 요청을 마저 끝내는 시간도 길어진다.
- **dev·CI 에는 내부 엔드포인트를 짧은 타임아웃으로 남긴다.** 채점하는 길이 환경마다 둘이 된다.
  배포에서만 도는 길은 dev·CI 의 시험이 덮지 못한다.

## 결과

- 채점하는 코드 경로가 하나다(태스크). 스캔은 넣기만 하므로 그 결과 행은 `queued` 다 —
  채점 결과는 시도 화면이 말한다.
- 채점 중인 태스크는 벤더를 기다리는 동안 트랜잭션(행 잠금)을 쥔다. 동시 채점 수(최대 8)만큼
  연결 풀러의 서버 연결을 그동안 쥔다(기본 풀 20).
- 배포가 채점 워커를 바꿀 때 최대 4분 걸린다. 그동안 새 채점은 Redis 에서 기다린다.
- 마이그레이션 하나(`scoring_queued_at`, null 허용 컬럼)는 ADR-0053 대로 먼저 돌고 뒤로
  호환된다.
- `core.tasks` 의 「진입점은 내부 HTTP 하나」는 이제 예외 둘(백업·강의실 채점)을 밝힌다.
