# 완성도 — 체크리스트 항목마다 0~5, 가중 합계, 같은 점수는 같은 등수

Status: Accepted (2026-11-05 결정)

## 맥락 (스펙 #882, 티켓 #883·#884)

지금 판정은 체크리스트 충족·미충족뿐이고, 클래스 「통과」도 공모전 Score(달성률)도 필수 항목만 센다. 그래서
통과자·상위 제출작이 대부분 동점이라 줄을 세울 수 없다. 대표·대장 grill(2026-11-05)이 정한 것:

- 새 기준을 만들지 않고 **기존 체크리스트 항목**(강의실 `ChecklistItem`, 공모전 `Requirement`)을 그대로 쓴다.
- 항목마다 AI 가 **0~5** 와 근거를 매긴다(필수·선택 모두). 가중치는 **필수 2, 선택 1**.
- **제출마다 절대 점수**다 — 제출끼리 비교해 정하지 않는다.
- **동점은 같은 등수**(1, 2, 2, 4).
- 기존 Score·통과·달성률·Distribution 의 뜻과 계산은 건드리지 않는다. 새 점수는 별도 기록이고 상금에 쓰지 않는다.

## 결정

### 용어 — 「완성도」

「루브릭」은 채점 지침과 헷갈려 CONTEXT.md 가 피하고, Score 쪽은 「점수·평가·Grade·Rating」을 피한다. 그래서
**완성도**다: 항목 하나의 0~5 는 「항목 완성도」, 합계(0~100)는 「완성도」, 줄 세운 것은 「완성도 순위」. 코드는
`quality` 계열(`core.quality_review`, `ClassroomQualityReview`)이다.

### 계산은 `core` 에 하나 (ADR-0037)

`core.quality_review` 가 두 앱이 함께 쓰는 것을 들고 있다 — `core` 는 기능 앱을 import 하지 않고, 앱은 자기 항목을
`QualityItemInput(item_id, label, required)` 으로 옮겨 넘긴다.

- 가중 점수 = Σ(가중치 × 항목 점수), 완성도 = 가중 점수 ÷ (5 × Σ가중치) × 100. 화면은 소수 첫째 자리까지.
- 등수는 **가중 점수(정수)** 로 매긴다(`competition_ranks`). 반올림한 완성도로 줄 세우지 않는다 — 동점을 줄이려는
  기능이다.
- 대상 항목은 체크리스트 행 전부다. **문법 검사는 넣지 않는다** — 체크리스트 행이 아니고 파서 판정이라
  「얼마나 잘」이 없다.
- 응답은 `{"scores": [{requirement_id, score, reasoning}]}`. 0~5 정수가 아니거나(실수·불리언·문자열 포함) 항목이
  빠지거나 겹치거나 근거가 비면 **그 채점은 실패**다(`QualityResponseError` → 어댑터가 `LLMAdapterError` 로 바꾼다).
  지어내지 않는다.
- 프롬프트: 제출물(소스)은 신뢰하지 않는 데이터라 `core.prompt_safety.neutralize_untrusted` 로 무력화해
  `<<<SOURCE_FILE_START>>>`·`<<<SOURCE_FILE_END>>>` 경계 안에 넣는다. 항목 라벨·채점 지침은 강사·개최자 입력이라 지금
  판정 프롬프트와 같은 방식으로 싣는다. 지금 판정 프롬프트는 이 변경으로 바뀌지 않는다.
- 체크리스트 지문 = 항목 (id, 라벨, 필수 여부) 묶음의 SHA-256(순서와 무관). 재사용 판정에 쓴다.
- 어댑터는 판정과 같은 왕복·같은 오류 분류를 쓰고 스키마·검증만 다르다 — `OpenAIScoringAdapter`·
  `AnthropicScoringAdapter` 에 `review_quality(_async)` 를 더했다(`QualityReviewAdapter` 프로토콜).

### 기록은 append-only

시도마다 `ClassroomQualityReview` 한 행 — 모델 버전, 프롬프트, 항목별 {항목 id, 라벨 스냅샷, 필수 여부, 0~5, 근거},
가중 점수, 최대 가중 점수, 완성도, 체크리스트 지문. 고쳐 쓰지 않는다(`save()` 가 막는다). 체크리스트를 고치면 새
행이 쌓이고, 「지금의 기록」은 같은 시도 + 같은 지문인 가장 최근 행이다. 대상은 참여자의 통과한 시도뿐이라
`PROTECT` 가 문제·클래스 삭제를 새로 막지 않는다(둘 다 참여자의 시도가 있으면 이미 거절한다).

### 클래스 — 대상·재사용·버튼

- **대상**: 문제마다 참여자(달성률과 같은 명단 — 강사·공동 강사·내보낸 사람 제외, `active_participant_q`)별
  **가장 최근 통과 시도** 하나. 통과는 `Problem.is_score_passed` 를 지금 체크리스트로 다시 센다 — 마지막 시도가
  실패여도 그 앞의 통과 시도가 대상이다. 한 번도 통과 못 한 사람은 순위에 없다.
- **재사용**: 대상 시도에 같은 지문의 기록이 있으면 그것을 쓴다. 시도가 바뀌었거나 체크리스트를 고쳤으면 다시
  매긴다. 이미 큐에 있는 사람은 다시 넣지 않는다.
- **비용 확인**: 「새로 채점할 n명 · 예상 비용」. `scoring_cost.attempt_cost` 를 그 문제의 채점 모델·추론 강도로
  쓰고, 프롬프트 길이는 완성도 프롬프트의 고정 부분 + **그 시도의 판정 프롬프트 길이**(같은 소스가 실렸다)로
  어림한다 — 확인 단계에서 소스를 다시 읽지(저장소 clone) 않으려는 것이고, 판정 프롬프트의 지시문만큼 조금 크게
  나온다. 단가표에 없는 모델이면 비용은 「단가 모름」.
- **막기**: 채점 연결이 없거나 키가 상했거나(`no_api_key`) 모델이 거부됐으면(`model_rejected`) 확인 단계가 그 사유를
  돌려주고 실행은 409 다 — 지금 판정 채점과 같은 판정(`pending_scoring.blocking_reason`).

### 큐 — 판정과 같은 grader, 칸은 따로

**별도 행(`ClassroomQualityJob`, 시도당 하나)** 을 두기로 했다. 판정 큐의 칸(`ClassroomSubmission.scoring_*`)에 얹으면
「채점됐는가(`ClassroomScore` 유무)」가 후보 조건에 박혀 있고 시도 하나에 임대 하나라는 전제가 섞여, 판정이 끝난
시도에 다시 임대를 찍으려면 판정 쪽 조건을 모두 갈라야 한다. 따로 두면 판정 흐름을 한 줄도 바꾸지 않는다.

- 버튼이 `queued_at` 을 찍는다(비었을 때만). 상주 grader 는 판정 후보를 먼저 집고 **남은 자리**로 완성도 작업을
  집는다(`_pick_quality`). **연결당 상한(8)은 판정과 함께 센다** — 같은 강사 키다. 전역 상한(64)도 같다.
- 임대·연장·결과 쓰기는 ADR-0059 그대로다: `SKIP LOCKED` 로 집고, 벤더 직전에 연장하고, 결과는 임대가 아직 내
  것인지 확인하는 짧은 트랜잭션에서 쓴다(`lock_timeout` 2초, 걸리면 `lock_busy` 로 다시 쓴다). 임대 길이도 같다(240초).
  grader 가 죽으면 임대 만료 뒤 다시 줍힌다 — 그래서 60초 안전망 스캔을 따로 두지 않는다(완성도는 강사가
  누를 때만 큐에 들어가고, 줍지 못한 작업은 큐에 남아 있다).
- 소스 읽기는 판정과 같은 함수(`_read_scoring_source`)를 DB 를 쓰지 않는 소스 풀에서 돌린다.
- **실패**는 그 시도만 「완성도 채점 실패」(`failed_at`·`error`)로 남기고 큐에서 뺀다. 자동으로 다시 하지 않고,
  강사가 다음에 누를 때 다시 들어간다. 키 거부·모델 거부·크레딧 소진·서버 연결 불가는 판정과 같은 자리로 옮긴다
  (다음 판정 채점과 버튼이 같은 사유로 막힌다).
- **사용량**은 `_record_token_usage` 로 그 클래스의 채점 사용량에 더한다(호환 서버가 usage 를 주지 않으면 판정과
  같은 어림).
- pytest 는 `CLASSROOM_GRADER_INLINE` 이라 버튼 자리에서 같은 세 걸음(임대·준비·결과)을 동기로 돈다.

### 공개 범위

- 강사(소유자·공동 강사)는 「완성도 순위」 전체 — 등수·참여자·완성도·항목별 0~5·근거.
- 문제마다 「참여자에게 공개」 스위치(`Problem.quality_public`, 기본 꺼짐, 강사가 문제 PATCH 로 바꾼다).
  복사·템플릿은 이 값을 옮기지 않는다.
- 켜면 참여자는 **자기 것만** 본다: 「완성도 순위 k등 / N명」, 자기 완성도, 항목별 점수·근거. 다른 참여자의
  이름·점수는 어느 응답에도 없다 — 순위표 전체를 보이는 것은 개인정보·위화감 문제가 있어 고르지 않았다.
- 꺼져 있으면 참여자 응답에 완성도가 아예 없다. 참여자의 완성도는 **따로 된 엔드포인트**
  (`GET …/problems/{id}/quality/mine`)로만 나가고 꺼져 있으면 404 다 — 기존 참여자 응답(`…/mine`)에 nullable 칸을
  더하지 않은 것은 「필드가 아예 없다」를 스키마 하나로 지키기 위해서다.
- 연결된 앱(MCP)으로는 내보내지 않는다(이번 범위 밖).

### 공모전 (#884)

같은 `core.quality_review` 를 쓴다(계산·프롬프트·응답 규율). 공모전 몫은 `scoring.quality` 에 있다.

- **언제**: 새 스캔 `submission-quality-review` 가 `submission-scoring` 과 나란히 60초마다 돈다. 「Score 는 있고 완성도는
  없는」 제출(같은 `Contest.Status.SCOREABLE` — 마감·심사기간 종료·선정 뒤)을 집는다. Score 흐름은 한 줄도 바꾸지
  않았다 — 완성도가 실패해도 Score·Distribution·Award 는 그대로다. 무료·유료 모두 대상이라 제품 스위치를 걸지 않는다
  (`submission-scoring` 과 같은 공용 스캔).
- **건너뛴다**: Score 가 「입력 없음」·「채점 실패」 자동 0%(`submissions.scoring_basis` 의 두 model_version)인 제출 —
  AI 가 소스를 읽지 않았다. Requirement 가 없는 공모전.
- **무엇을 읽나**: 소스를 다시 읽거나 저장소를 다시 clone 하지 않는다. **Score 프롬프트의 「## Requirements」 절부터
  끝까지**(Requirement·자가 응답·Evidence·선별된 소스)를 제출물로 싣는다 — Score 와 같은 것을 보고 매기고, 스토리지·
  GitHub 를 한 번 더 치지 않는다(마감 뒤 저장소가 비공개로 바뀌어도 같은 근거다). 그 글은 참가자 데이터라
  `build_prompt` 가 `neutralize_untrusted` 로 무력화해 경계 안에 넣는다. 공모전엔 채점 지침 입력이 없어 지침 자리에
  고정 문장(「별도 지침 없음 — 체크리스트 문구 그대로 판단한다」)을 둔다.
- **키**: `core.llm_scoring.get_adapter()` — Score 와 같은 플랫폼 어댑터. 흉내 어댑터(`FakeLLMScoringAdapter`)는
  제출·항목 번호로 정한 1~5 를 낸다(공모전 입력엔 Requirement 문구가 함께 실려 「문구가 소스에 있나」로는 갈리지 않는다).
- **기록**: `SubmissionQualityReview`(append-only, `AppendOnlyModel`) — 제출당 하나(`OneToOneField`, 마감 뒤엔
  Requirement 를 고칠 수 없다; 겹친 스캔의 삽입도 막는다). 남기는 것은 강의실과 같다. **`on_delete=CASCADE`** 다
  (Score 는 PROTECT): 이 행은 Score 가 있는 제출에만 생기고 Score 의 PROTECT 가 이미 제출·공모전 삭제를 막는다. 그
  막음을 넘는 길은 시드 정리(`hard_delete_demo_seed_scores`·`hard_delete_e2e_fixture_rows`)뿐이라, 그때 함께
  지워지게 했다.
- **실패**: `QualityReviewAttempt`(`ScoringAttempt` 와 같은 운영 로그). 영구 실패(`LLMAdapterPermanentError`)가
  하나라도 있거나 5번 실패하면 더 집지 않는다. Score 와 달리 0% 같은 대체값을 만들지 않는다 — 상금과 무관하니
  「없음」으로 남겨도 아무것도 막지 않는다. 사용량 기록(`_record_token_usage`)은 강의실 채점 연결 몫이라 타지 않는다 —
  공모전 Score 채점도 사용량을 따로 남기지 않는다.
- **개최자**: 비교 목록(`GET /contests/{id}/submissions/compare`)의 제출마다 `quality` — 완성도·가중 점수·최대·
  항목별 0~5·근거·**등수**(완성도가 매겨진 제출끼리, `competition_ranks`). 아직 없으면 null. 화면은 「완성도」 줄,
  요구사항 칸의 「항목 완성도 n/5」·근거, 「제출순」·「완성도순」 정렬(가중 점수 → 제출 순서, 없는 것은 뒤).
- **제출자**: `GET /submissions/{id}/score` 의 `quality` — 본인 것뿐이고 **등수가 없다**(등수는 남의 제출과 견준
  값이다). 남의 제출은 이 API 가 403 이고, 공개 단건·비교 목록 등 다른 응답에는 완성도 필드가 없다.
- **이의**: 지금처럼 Score 에만 건다. `can_appeal`·이의 접수는 완성도와 무관하다.

## 고려한 대안

- **판정 큐 칸을 다시 쓴다.** 위 「큐」 — 판정의 「채점됐는가」 조건과 섞인다.
- **Celery 태스크로 돌린다.** ADR-0059 가 강의실 채점을 grader 하나로 모았다. 같은 키의 동시성 상한을 함께 세려면
  같은 프로세스에 있어야 한다.
- **판정과 한 호출로 0~5 를 함께 받는다.** 통과·Score 의 뜻을 건드리지 않는다는 결정과, 통과한 시도만 매긴다는
  대상 규칙에 맞지 않는다(모든 시도에 비용이 든다).
- **반올림한 완성도로 등수를 매긴다.** 동점이 다시 늘어난다.
