# 운영 백오피스는 Django admin이 아니라 운영자 API와 별도 앱으로 간다 (ADR-0002 개정)

ADR-0002는 "운영 백오피스는 Django admin으로 공짜로 시작하고, 필요해지면 `admin/`의 별도 SPA로 옮긴다"고 적었다. 그 이동을 지금 한다.

미루지 않는 이유가 있다. **Django admin은 모델 행을 직접 편집할 수 있다.** Appeal과 Ruling을 admin에서 고칠 수 있는 한 감사 추적에는 우회로가 열린 채로 남는다 — 감사 추적을 세우는 결정이 스스로 그 문을 열어두는 꼴이다. 그리고 admin의 비밀번호 로그인 화면이 모든 환경에 무조건 노출된다: `config/urls.py`는 조건 없이 `admin/`을 마운트하고, 지금 14개 앱이 admin을 등록해 두었다.

**`admin/`을 완전히 내린다.** URL, `django.contrib.admin`, 각 앱의 `admin.py`를 전부 제거한다. 사람이 판단하는 행위는 `/api/operator/*`로만 한다.

**`InternalAuth`는 자동 스캔 전용으로 남는다.** Celery beat가 부르는 틱들이 그것이다. 사람이 부르라고 만들어 둔 `/api/internal/appeals*` 셋(목록·상세·심판)은 운영자 API로 옮긴다 — 공유 시크릿만 알면 신원 없이 돈을 움직일 수 있는 경로가 남아 있으면 ADR-0018이 성립하지 않는다.

## Consequences

**운영자 앱이 나오기 전까지 운영 화면이 없다.** 그동안 Operator는 HTTP로 운영자 API를 직접 친다. dev에서 데이터를 훑던 수단도 사라지므로 `manage.py shell`이나 psql을 쓴다. 이것이 이 결정의 실질적인 비용이고, 운영자 앱 스펙이 그 비용을 갚는다.

**운영자 앱도 BFF다** — ADR-0016과 같은 모양이다. 세션 쿠키는 앱 서버가 들고 백엔드는 same-origin 세션과 `Origin` 검증만 다룬다. 그래서 CORS 허용목록도, `SameSite=None` 쿠키도 필요 없다. 돈을 움직이는 경로를 크로스 오리진 쿠키 위에 올리지 않는다.

**계정 관리 화면이 없으므로 부트스트랩 경로를 코드로 둔다.** 첫 Operator는 관리 명령으로 만들고, 이후는 `is_superuser`가 운영자 API로 만든다. 관리 명령이 서로소 불변식(ADR-0018)을 강제하는 자리이기도 하다 — `createsuperuser`는 그 불변식을 모른다.

**admin 제거의 파급을 확인해야 한다.** 14개 앱이 admin을 등록해 두었지만 그 화면들에 대한 테스트도 운영 절차 문서도 없다. 실제로 무엇을 잃는지 확인한 뒤 지운다.

**운영자 API는 HTTP 시임 위에 그대로 올라간다.** 이 저장소의 테스트 규율(CLAUDE.md)이 바뀌지 않는다 — 세션 로그인도, 심판도 전부 마운트된 API를 전체 요청 스택으로 쳐서 검증한다. 화면이 없어도 인수 기준은 전부 검증 가능하다.
