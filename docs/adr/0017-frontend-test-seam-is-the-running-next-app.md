# 프론트엔드의 테스트 시임은 실행 중인 Next 앱 하나다

백엔드에서 "시임은 HTTP 하나"라는 규율이 코드리뷰가 141건을 잡아내는 기반이 됐다. 프론트엔드에도 같은 질문에 답해야 하고, 나중에 바꾸면 테스트를 전부 다시 쓴다.

다만 지켜야 할 것이 다르다. API 로직은 이미 백엔드 테스트가 지키므로 프론트가 다시 검증할 필요가 없다. 프론트에만 있는 위험은 셋이다.

1. **공개 페이지가 실제로 서버 렌더링되는가** — Next.js를 도입한 이유 전체(ADR-0015)가 여기 걸려 있는데, 페이지 하나에 `"use client"`가 붙는 것만으로 조용히 깨진다.
2. **인증 구역이 실제로 막히는가** — 미들웨어 가드가 도는지.
3. **프록시 허용목록과 Origin 검증이 실제로 막는가** — 뚫리면 ADR-0016의 CSRF 방어가 무효다.

셋 다 모킹으로는 검증되지 않는다. 그래서 **실행 중인 Next 앱을 유일한 진입점으로 삼고 Playwright로 친다.** 브라우저가 필요한 것은 `page`로, 아닌 것(프록시 허용목록·Origin 검증)은 raw `request`로 — 같은 시임, 같은 입구다. 백엔드는 모킹하지 않고 compose로 실제로 띄운다.

## Consequences

- 색인 검증은 **JS를 끈 상태의 HTML에 내용이 있는지** 직접 확인한다. 서버 렌더링을 "믿는" 대신 관찰한다.
- 컴포넌트 단위 테스트를 쓰지 않는다. 구현 결합을 피하고 시임을 하나로 유지하기 위해서다.
- CI가 느려지고 백엔드 컨테이너를 띄워야 한다. 대신 백엔드가 이미 로직을 지키고 있으므로 프론트 테스트는 얇게 유지할 수 있다 — 위 세 가지와 핵심 사용자 흐름까지다.
- Fake 어댑터(ADR-0007)를 그대로 쓰므로 실제 PG·LLM·알림 벤더 없이 전 흐름을 돌릴 수 있다.
