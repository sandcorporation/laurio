# 공개 표면만 서버 렌더링하고, 로그인 이후는 클라이언트에 둔다

`REQUEST.md`는 개발자 공개 프로필이 "검색엔진에 색인되는 공개 URL"을 가진다고 규정한다. 이건 부가 기능이 아니다 — 순수 콘테스트를 택하면서 탈락한 개발자에게 남는 보상 전체가 "그 포트폴리오가 플랫폼 밖에서 발견된다"에 걸려 있다. 순수 클라이언트 렌더링 SPA로는 그게 위태롭다. 구글은 JS를 렌더링하지만 색인이 느리고 불확실하며, 한국 시장에서 결정적인 네이버 크롤러는 JS 렌더링이 약하다.

그래서 Next.js를 쓰되, **서버 렌더링은 공개 표면에만** 적용한다. 로그인 이후 화면은 클라이언트에서 렌더링한다.

경계는 발명하지 않았다. 백엔드가 이미 그어둔 선을 그대로 쓴다 — django-ninja에서 `auth=None`인 엔드포인트가 곧 공개 표면이다: 공모전 목록·상세, 개발자 공개 프로필, 마감 후 공개된 제출물, 카테고리·요구형태·견적.

**인증 경계와 렌더링 경계가 같은 선이다.** 이게 이 결정의 핵심이며, ADR-0016이 성립하는 이유이기도 하다: 서버가 렌더링하는 페이지는 인증이 필요 없으므로, 서버가 사용자 토큰을 다룰 일이 애초에 없다.

## Consequences

- 인증 구역에서는 서버 컴포넌트와 서버 액션을 쓰지 않는다. Next 안에 클라이언트 SPA가 들어앉은 형태가 되며, 그건 의도된 것이다. Next의 이점은 공개 표면에서만 취한다.
- 공개 페이지에 `"use client"`가 실수로 붙으면 색인 약속이 조용히 깨진다. 그래서 ADR-0017의 테스트가 JS를 끈 상태의 HTML을 직접 확인한다.
- 공개 페이지는 OG 태그와 구조화 데이터를 서버에서 넣을 수 있다. 개발자 프로필이 공유될 때 제 모습으로 미리보기된다.
- 두 렌더링 모드가 한 앱에 공존하므로, 어느 쪽인지 헷갈리는 페이지가 생기면 그건 경계가 잘못 그어진 것이다 — `auth=None` 여부로 되돌아가 판정한다.
