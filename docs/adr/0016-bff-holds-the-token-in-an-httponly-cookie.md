# 웹 프론트엔드는 BFF로 토큰을 HttpOnly 쿠키에 보관한다 (ADR-0012 개정)

ADR-0012는 JWT를 localStorage에 두기로 하면서 근거를 이렇게 적었다: "SPA(frontend, admin)와 향후 모바일까지 붙이기 쉬운 구성을 우선해". 전제가 **순수 SPA**였다. ADR-0015가 Next.js를 도입하면서 그 전제가 바뀌었고, 그래서 이 결정을 다시 연다.

localStorage 토큰을 Next.js에서 그대로 쓰면 서버가 토큰을 읽을 수 없어 미들웨어로 라우트를 보호할 수 없다. 로그인하지 않은 사람이 인증 경로에 직접 들어가면 화면이 한 번 번쩍인 뒤에야 리다이렉트된다. 그리고 ADR-0012가 스스로 인정한 구멍 — XSS로 토큰이 밖으로 빠져나가는 경로 — 이 그대로 남는다.

이제 서버가 생겼으므로 그 구멍을 닫는다. **토큰은 HttpOnly 쿠키에 두고, Next 라우트 핸들러가 꺼내서 Django에 Bearer 헤더로 프록시한다.** 브라우저 JS는 토큰을 볼 수 없다.

**Django의 인증 방식은 바뀌지 않는다.** 여전히 Bearer를 받는다. 쿠키는 웹 프론트엔드와 Next 사이에만 존재하므로, ADR-0012가 지키려던 "향후 모바일" 경로는 그대로다.

## Consequences

**CSRF가 다시 살아난다 — 이 결정의 성립 조건이다.** localStorage에는 주변 권한이 없어 CSRF가 성립하지 않았다. 쿠키로 옮기면 악성 사이트가 브라우저에게 우리 오리진으로 요청을 시킬 수 있고, 쿠키가 자동으로 붙어 Next가 유효한 Bearer를 달아 전달한다. 따라서 다음 둘이 반드시 함께 간다. 빠지면 이 결정은 localStorage보다 나쁘다.

- 쿠키에 `SameSite` 를 건다
- 프록시가 변경 요청의 `Origin` 을 검증한다

**프록시는 catch-all 한 파일이되, 통과시킬 경로를 명시적 허용목록으로 관리한다.** Django에는 라우터가 18개이고 그중 `/api/internal/*` 여섯 개는 마감 전이·배분·환불·지급·채점·알림 발송을 실행한다. 허용목록에 없으면 통과하지 않으므로, 백엔드에 새 엔드포인트가 생겨도 검토 없이 웹에 노출되는 일이 없다.

**ADR-0012의 세 보완책 중 둘은 여전히 유효하다.** 사용자 입력 서식 sanitize와 CSP 헤더는 그대로 간다. 세 번째(짧은 액세스 토큰 + 리프레시 회전)도 유지하되, 토큰이 JS에 노출되지 않으므로 유출 시 피해 시간을 줄이는 의미는 줄어든다.

**프록시 홉이 하나 늘어난다.** 파일 업로드는 영향이 없다 — ADR-0005대로 presigned URL을 받아 브라우저가 스토리지로 직접 올리므로 바이트는 프록시를 타지 않는다.
