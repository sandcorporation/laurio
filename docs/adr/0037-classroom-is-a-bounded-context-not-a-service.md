# Classroom 은 경계지 서비스가 아니다

Status: Accepted (2026-09-10 결정)

과제-제출 쪽을 `classroom.laurio.…` 라는 별도 제품으로 세운다. 공모전은 나중을 위한
기능이 되고 당분간 그쪽에 손을 대지 않는다.

「분리」를 어떻게 할 것인가를 먼저 정한다. 후보는 둘이었다 — **서비스로 쪼개기**(별도
배포 단위·별도 DB)와 **경계로 쪼개기**(배포는 그대로, 임포트를 규칙으로 막기).

## 서비스로 쪼개지 않는다

MSA 가 보통 사 주는 것 넷을 이 저장소에 대 보면 지금은 하나도 사지 못한다.

- **팀 분리** — 해당 없다. 한 사람과 에이전트가 만든다.
- **기술 스택 분리** — 필요 없다. 양쪽 다 Django + Next 다.
- **독립 확장** — 부하 근거가 없다. staging 의 제출물이 43건이다.
- **장애 격리** — 유일하게 실질이 있는 항목인데, 위험한 것은 Classroom 의 채점(강사
  키·외부 API)뿐이고 그건 큐를 가르는 것으로 얻어진다.

값은 그 반대다. 원장과 `Score` 가 append-only 라 경계를 넘으면 분산 트랜잭션이 생기고,
회원을 공유하기로 했으므로 두 DB 사이 사용자 동기화라는 새 실패 지점이 선다. 무엇보다
이 저장소의 테스트 전략 — **「HTTP 가 유일한 시임」, 전체 요청 스택을 통과하는 1638건**
— 이 서비스 경계에서 깨진다. 그 전략이 이 저장소가 빠르게 움직여 온 이유다.

## 경계는 진짜로 긋는다

배포 단위를 그대로 두는 대신 임포트 경계를 **기계가** 지킨다. `scripts/` 의 검사 하나와
CI 잡 하나 — `adr-status`·`screen-language` 가 이미 쓴 관용구다. 금지는 **양방향**이다:
`classroom` 이 공모전 계열(`contests`·`payments`·`ledger`·`awards`·`appeals`·`payouts`·
`distributions`·`handovers`·`verification`)을 임포트하지 못하고, 그 반대도 못 한다.
둘 다 쓰는 것(`accounts`·`core`·`storage`·`notifications`·`scoring` 어댑터)은 공유층으로
묶는다.

양방향인 이유는 한 방향만 막으면 공모전 쪽이 나중에 `classroom` 을 참조하기 시작할 때
막을 근거가 없어서다. 그리고 그 표 자체가 아키텍처 문서가 된다 — 어느 쪽을 지워도 다른
쪽이 사는지가 한 파일에서 읽힌다.

## 「앱을 내리면 테스트가 빨라진다」는 사실이 아니다

경계를 그으면 `INSTALLED_APPS` 를 줄여 테스트를 빠르게 할 수 있다고 기대했지만, 재 보니
그렇지 않다. 전체 스위트를 DB 새로 만들기와 재사용으로 각각 돌리면 **97초 대 99초**로
차이가 오차 범위다 — 마이그레이션 95개를 적용하는 비용은 워커 6개를 합쳐도 사실상 0이고,
97초는 테스트 자체가 쓰는 시간이다.

빨라지는 길은 **덜 돌리는 것**이다. 경계가 그어져 있으면 「classroom 을 건드렸으니
classroom 테스트만」이 안전하게 성립한다. 그건 앱 로딩이 아니라 테스트 **선택**의 문제라,
경계의 값은 여전히 크지만 그 값이 나오는 자리가 다르다.

## 이름이 「LMS」가 아닌 이유

이 저장소에는 이미 `LMS` 가 있다 — `NotificationDispatch.Channel.LMS`, 장문 문자(Long
Message Service)이고 `AligoLmsAdapter` 가 실물로 붙어 있다(ADR-0009). 같은 약어에 두 뜻을
얹으면 알림 코드를 읽는 사람이 매번 어느 쪽인지 가려야 한다 — `CONTEXT.md` 가 막아 온
종류의 사고다. 제품·서브도메인·Django 앱 이름을 모두 `classroom` 으로 맞춘다.

## 되돌리기

경계가 그어진 코드는 나중에 서비스로 쪼갤 수 있지만, 안 그어진 코드는 못 쪼갠다. 이
결정은 MSA 를 **포기**하는 것이 아니라 **미루는** 것이고, 미루는 동안 그 선택지를 살려
두는 값을 지금 치른다.
