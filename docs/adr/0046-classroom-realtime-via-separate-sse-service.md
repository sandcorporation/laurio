# 강의실은 제출 즉시 채점 작업을 넣고, 바뀐 사실을 별도 SSE 서비스가 BFF 를 거쳐 알린다

Status: Accepted (2026-09-14 결정)

구현은 후속 스펙·티켓이 한다 — 이 ADR 이 들어온 시점에 코드는 아직 아래 「문제」의 모양이다.

## 문제

참여자가 제출하면 채점이 **곧바로 시작되지 않는다.** 제출 API 는 시도만 저장하고,
Celery beat 가 60초마다 도는 `classroom-submission-scoring` 스캔이 점수 없는 시도를
한 번에 50개씩 차례로 집는다. 그래서 채점 시작까지 최대 1분이 걸린다. 문서가 적은
「제출 즉시 비동기로 채점」은 실제로는 「1분 안에 주기 스캔이 집어 간다」였다.

화면도 그 결과를 스스로 알지 못한다. 제출 화면의 「내 시도」는 자동 갱신이 없어
「채점 중」이 「채점 완료」로 바뀌려면 새로고침해야 하고, 강의실 알림 벨은 30초
폴링이다. 마감 없이 고쳐 내고 다시 내는 것이 강의실의 정상 흐름(CONTEXT.md 「Problem」)
이라, 이 대기는 한 번이 아니라 시도마다 반복된다.

## 결정

**채점 시작.** 제출이 커밋되면 그 시도 하나를 채점하는 작업을 곧바로 큐에 넣는다.
60초 스캔은 없애지 않고 **안전망**으로 남긴다 — 작업이 유실되거나 실패한 시도를
줍는다. 두 경로는 같은 채점 함수를 쓰고 행 잠금으로 겹치지 않아, 시도당 Score 가
정확히 하나라는 계약(ADR-0006)이 그대로다. dev·CI 는 지금처럼 워커가 없어 작업이
돌지 않고 e2e 는 스캔을 직접 부른다(Celery 를 dev 기본 기동에서 뺀 이유, #40).

**실시간 전달은 SSE 이고, API 서버가 아니라 별도 서비스가 연다.** 같은 backend
이미지를 ASGI 로 띄우는 이벤트 서비스를 하나 더 두고, 그 서비스가 Redis pub/sub
으로 받은 사실을 스트림으로 흘린다. 브라우저는 **강의실 BFF 를 거쳐** 붙는다 —
쿠키를 JWT 로 바꾸고 허용목록·Origin 을 검사하는 문(ADR-0016)이 스트림에도 그대로
선다. 스트림에는 **「바뀌었다」는 신호만** 싣는다(무슨 일이 어느 시도·알림에
일어났는가의 식별자). 화면은 신호를 받으면 기존 API 를 다시 부른다.

탭마다 스트림 하나를 강의실 레이아웃이 열고 화면들이 나눠 쓰며, 보이지 않는 탭은
닫는다. 스트림이 끊기거나 막히면 폴링으로 물러나고, 다시 붙으면 한 번 재조회한다.
대상은 강의실 네 자리다 — 참여자 「내 시도」, 강의실 알림 벨, 참여자 문제 목록의
통과 표시, 강사 제출 현황(새 제출과 채점 완료). 공개 앱은 이번 범위가 아니다.

## 고려한 대안

- **스캔 주기만 줄이기(10~15초).** 코드는 가장 적게 바뀌지만 대기는 여전히 수십
  초이고 빈 스캔이 잦다. 즉시 작업을 넣으면 스캔을 짧게 돌릴 이유가 사라진다.
- **필요할 때만 짧게 폴링.** 새 인프라가 없고, 즉시 채점과 합치면 체감은 SSE 와
  비슷하다. 그래도 알림·강사 현황까지 네 자리가 제각각 짧게 치는 모양보다
  서버가 밀어 주는 쪽을 골랐다 — 폴링은 막힌 환경의 물러날 자리로 남긴다.
- **WebSocket.** 지금 필요한 것은 서버→브라우저 한 방향뿐인데, Django Channels 와
  WS 인증 경로가 더해지고 Next BFF 가 WS 를 중계하지 못해 ADR-0016 의 문을 우회하는
  길이 생긴다.
- **API 서버 자체를 ASGI 로, 또는 gunicorn gevent 워커로.** 지금 API 는 동기
  gunicorn 워커 3~4개라 SSE 연결 하나가 워커 하나를 붙잡는다 — 그래서 어떻게든
  갈라야 한다. 전체를 ASGI 로 바꾸면 동기 ORM 코드와 미들웨어(운영자 세션 등)를
  전부 다시 검증해야 하고, gevent 는 몽키패칭이 psycopg·boto3·OpenAI 클라이언트에
  두루 걸려 재현하기 어려운 문제를 만든다. 스트림만 따로 떼면 나머지는 그대로다.
- **브라우저가 이벤트 서비스에 직접 붙기.** Next 를 거치지 않아 가볍지만 BFF 밖에
  새 인증 문이 생기고 리버스 프록시·CORS·쿠키 설정을 저장소 밖에서 더 해야 한다.
- **스트림에 바뀐 데이터까지 싣기.** 요청은 하나 줄지만 같은 데이터의 모양과 권한
  (강사·참여자·내보내진 참여자)이 기존 엔드포인트와 스트림 두 곳에 생겨 갈라진다.

## 결과

- 배포 서비스가 하나 는다 — `deploy.sh` 의 경로→서비스 팬아웃과 헬스 체크, 세 compose
  파일이 그것을 알아야 한다. 저장소 밖의 TLS 리버스 프록시는 스트림 응답을 버퍼링하지
  않아야 한다.
- 채점이 스캔 한 곳이 아니라 두 곳에서 시작되므로, 채점을 건드리는 변경은 두 경로를
  함께 본다.
- 신호가 빠져도 화면은 기존 API 로 다시 맞춰진다 — 스트림은 빠르게 만드는 장치이지
  진실의 출처가 아니다.
