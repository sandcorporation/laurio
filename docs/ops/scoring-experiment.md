# 채점 방식 비교 실험 — `compare_scoring_methods`·`experiment_report`

스펙 #1244, 티켓 #1246. 채점 방식(한 번 호출·CLI 에이전트·우리 루프) × 모델을 **이미 채점된** 제출에 돌려 실험 표
(`ScoringExperiment`·`ScoringExperimentRun`)에만 남긴다. 운영 점수·`AgentRun`·점수 정정·순위·지급은 바뀌지 않고, 운영
설정(`CONTEST_SCORING_METHOD`·벤더·모델)도 읽거나 바꾸지 않는다 — 벤더·모델은 줄마다 인자로 간다.

입력은 운영 채점이 실제로 본 것이다: 정정 채점과 같이 `Score` 에 남은 처음 커밋으로 저장소를 다시 받는다
(`scoring.corrections._fixed_inputs`). 에이전트·우리 루프는 입력이 하나(저장소 하나 또는 zip 소스 하나)일 때만 돈다 —
아니면 그 칸은 「실패(박제본 없음)」다(운영이면 한 번 호출로 간다).

## 어디서 돌리나 — celery-worker

에이전트·우리 루프 줄은 실행기 `agent-grader:8003` 을 부른다. 운영에서 실행기와 같은 네트워크(`agent-call`)에 있는
것은 **celery-worker 뿐**이다 — backend 는 `default` 네트워크에만 있어 닿지 못한다(운영 채점도 celery-worker 에서 돈다).
그래서 `compare_scoring_methods` 는 celery-worker 에서 돌린다. `experiment_report` 는 DB 만 읽으니 어느 컨테이너든 된다.

- 줄에 에이전트·우리 루프가 있으면 명령이 실행기의 `GET /health` 에 먼저 한 번 닿아 본다. 미리 보기는 그 결과를 한 줄
  찍는다(「실행기 agent-grader:8003 에 닿는다.」 또는 「… 에 닿지 못한다(URLError) — celery-worker 에서 돌린다」).
- 못 닿으면 `--confirm` 이어도 실험·칸을 하나도 만들지 않고 0 아닌 코드로 끝난다.

## 인프라 실패는 결과가 아니다

다음은 방식의 실패가 아니라 인프라 실패다 — 칸으로 남기지 않고, 같은 인자(같은 이름)로 다시 부르면 그 칸이 다시 돈다.

- 실행기에 닿지 못함·HTTP 오류(`AgentGraderError`), 동시 실행이 참(`AgentGraderBusy`)
- 실행 토큰 거절(`RunTokenRefused`, 실행 도중 프록시 401·403)
- 벤더 계정 쪽 거절(`AgentVendorRefused`)·실행 도중 하루 상한 429(`experiment_daily_limit`·`daily_limit`)

#1257 전에는 이런 칸도 `failed` 로 남았다. 그런 칸(`problem` 이 위 예외 이름으로 시작하는 `failed`)은 끝난 칸으로 세지
않고 보고표에도 넣지 않는다 — 다음 실행이 그 자리를 결과로 바꾼다. 데이터는 고치지 않는다.
모델이 답을 냈는데 틀린 꼴이거나 시간·실행 예산을 넘긴 것은 지금처럼 실패·보류 칸이고, 이것이 보고표의 실패율이다.
인프라 실패가 **연속 3칸**이면 거기서 멈추고 「남은 칸 N개」를 찍는다(0 아닌 코드).

## 돈은 따로 센다

- 에이전트·우리 루프는 실행 토큰 용도 `experiment` 로 `llm-proxy` 를 지난다. 프록시는 이 토큰을 운영 하루 상한
  (`AGENT_SCORING_DAILY_LIMIT_USD`)에 세지 않고 **실험 하루 상한 `AGENT_EXPERIMENT_DAILY_LIMIT_USD`** 에만 센다.
  넘으면 429 `experiment_daily_limit`.
- 한 번 호출은 벤더를 직접 부르므로 비용을 실험 표(`cost_usd`)에 적고 같은 하루 합계에 넣는다.
- 명령은 칸마다 먼저 「상한 − 오늘 쓴 돈 ≥ 이 줄의 칸당 최대 비용」을 본다. 모자라면 거기서 멈춘다.
- **기본값 0 은 꺼짐이다** — 상한을 정하기 전에는 `--confirm` 을 줘도 한 칸도 돌지 않는다.

## 순서

먼저 **2건 × 1회**로 단가를 실측하고(대장 #4345), 보고표의 「전체 예상」을 사람이 본 뒤 같은 실험을 전체로 넓힌다.

1. **미리 보기** — `--confirm` 없이 부른다. 모델을 부르지 않고 실험 표도 만들지 않는다.

   ```bash
   docker compose -f docker/compose.prod.yaml exec celery-worker \
     python manage.py compare_scoring_methods --contest 3 --repeat 3 --limit-submissions 16
   ```

   찍는 것: 실험 이름, 제출 수 × 회차, 남은 칸, 줄마다 남은 칸·예상 비용 범위·칸당 최대, 합계, 실험 하루 상한·오늘 쓴 돈·남은 돈.
   `--rows` 를 비우면 기본 줄 일곱이다 — 기준 `agent:claude-sonnet-5-5`, 그리고 `claude-haiku-5-5`·`gpt-4.1-mini` 마다
   `single_call`·`agent`·`self_loop`. 첫째 줄이 보고표의 기준 줄이다.
   예상 비용은 공모전 3 실측에서 잡은 토큰 범위 × 단가(에이전트·우리 루프는 실행 예산 $1 로 자른다)이고, 같은 실험이
   이미 돈 칸이 있으면 그 줄의 실제 최소·최대로 바뀐다. 단가는 실제 비용과 같은 계산(`usage_cost_usd`)이다 — 한 번 호출의
   높은 쪽은 입력 300k 로, Haiku 5.5 의 10만 토큰 초과 5배 단가까지 넣어 공모전 3 실측(입력 100k~255k)을 덮는다.
2. **금액 확인** — 합계 예상의 높은 쪽을 보고 사람이 쓸 돈을 정한다.
3. **상한 설정** — 운영자 앱 「운영 설정」의 `AGENT_EXPERIMENT_DAILY_LIMIT_USD`(「기타」 묶음)에 그날 쓸 금액을 저장한다.
4. **단가 실측** — `--limit-submissions 2 --repeat 1 --name <이름> --confirm`. 제출은 id 오름차순으로 앞의 2건이다.
   보고표(`experiment_report <이름>`)의 「실측 건당 비용」과 「전체 예상」(실측 건당 비용 × 공모전의 채점된 제출 전부 × 회차 3)을
   보고 전체 실행 금액을 정한다. 회차 1 보고표의 흔들림은 「회차 1 — 잴 수 없음」이다.
5. **전체 실행** — 같은 `--name` 에 `--repeat 3`(건수 제한 없이) `--confirm`. 줄이 같으면 같은 실험이 넓어지고, 이미 돈
   2건 × 1회는 다시 돌지 않는다. 칸마다 한 줄(상태·점수·비용)을 찍는다.
6. **이어 가기** — 상한에 멈췄으면 「남은 칸 N개」가 찍힌다. 다음 날(또는 상한을 올린 뒤) **같은 인자로** 다시 부르면
   같은 실험(인자에서 만든 이름, 또는 `--name`)의 남은 칸만 돈다. 끝난 칸은 다시 돌지 않는다(방식의 실패 칸도 — 실패율이
   보고표의 숫자다). 인프라 실패 칸은 끝난 칸이 아니라 다시 돈다(위 절).
7. **끝나면 상한을 0 으로** 돌려 둔다.
8. **보고표** — `python manage.py experiment_report <실험 이름>`(마크다운), `--format csv`(CSV).

## 보고표가 말하는 것

줄마다: 제출·회차·채점·보류·실패 수, 기준 줄 대비 평균 점수 차(제출별 회차 평균끼리의 절댓값 평균)·최대 차, 순위 일치
(스피어만), 흔들림(제출별 회차 표준편차의 평균), 근거 실재율, 실측 건당 비용, 전체 예상(제출 N × 회차 3), p50·p90 시간.
돈이 든 칸이 하나도 없는 줄(인프라 실패만 있었다 등)의 전체 예상은 「실측 없음」이고 합계에서 빠진다 — 머리 줄이 몇 줄이
빠졌는지 말한다. 실험의 줄 가운데 남은 칸이 없는 줄도 빈 줄(회차 0)로 보인다.
그리고 문턱 여덟(스펙 #1244 넷 + 대장 #4345 설계안, 줄마다 통과·미달, 판단할 수 없으면 「—」):

| 문턱 | 통과 |
| --- | --- |
| 평균 차 | 기준 줄 대비 평균 점수 차 ≤ 5점 |
| 최대 차 | ≤ 15점 |
| 순위 일치 | 스피어만 ≥ 0.8 |
| 흔들림 | ≤ 기준 줄의 흔들림 + 2 |
| 근거 | 근거 실재율 ≥ 95% |
| 실패·보류 | (실패 + 보류) / 회차 ≤ 1/16 |
| 비용 | 실측 건당 비용 ≤ 기준 줄의 1/3 |
| 시간 | p90 ≤ 300초 |

근거 실재율은 모델이 낸 `경로:줄` 을 박제본에서 우리 루프와 같은 검사(`selfloop.check_evidence`)로 확인한 몫이다. 우리
루프는 확인하지 못한 근거를 판정에 남기지 않으므로, 다시 물어 버린 근거(`evidence_dropped`)를 분모에 넣는다. 한 번
호출은 근거를 `경로:줄` 로 내지 않아 「—」다. 머리에는 표본 수와 한계(평균 차의 95% 신뢰 구간 반폭, 회차·제출이 적을 때의
경고)가 붙는다.

## 표본을 늘리는 길 (제안 — 결정 아님)

- 공모전 하나의 제출은 수십 건이라 평균 차 ±5점을 가르기 어렵다. 끝난 공모전 여럿을 같은 줄로 돌려 보고표를 합치는
  `--contest` 여러 개 받기.
- 운영 채점 대기와 겹치지 않는 시간대에 날마다 상한만큼 이어 돌리는 예약 실행.
- 사람이 매긴 점수(이의 심사 결과)가 있는 제출을 따로 묶어, 기준 줄 대신 사람 점수와 견주는 줄.
