# 채점 방식 비교 실험 — `compare_scoring_methods`·`experiment_report`

스펙 #1244, 티켓 #1246. 채점 방식(한 번 호출·CLI 에이전트·우리 루프) × 모델을 **이미 채점된** 제출에 돌려 실험 표
(`ScoringExperiment`·`ScoringExperimentRun`)에만 남긴다. 운영 점수·`AgentRun`·점수 정정·순위·지급은 바뀌지 않고, 운영
설정(`CONTEST_SCORING_METHOD`·벤더·모델)도 읽거나 바꾸지 않는다 — 벤더·모델은 줄마다 인자로 간다.

입력은 운영 채점이 실제로 본 것이다: 정정 채점과 같이 `Score` 에 남은 처음 커밋으로 저장소를 다시 받는다
(`scoring.corrections._fixed_inputs`). 에이전트·우리 루프는 입력이 하나(저장소 하나 또는 zip 소스 하나)일 때만 돈다 —
아니면 그 칸은 「실패(박제본 없음)」다(운영이면 한 번 호출로 간다).

## 어디서 돌리나 — celery-worker

에이전트·우리 루프 줄은 실행기 `agent-grader:8003` 을 부른다. 운영에서 실행기와 같은 네트워크(`agent-call`)에 있는
것은 **celery-worker 뿐**이다 — backend 는 `default` 네트워크에만 있어 닿지 못한다(운영 채점도 celery-worker 에서 돈다).
그래서 `compare_scoring_methods` 는 celery-worker 에서 돌린다. `experiment_report` 는 DB 만 읽으니 어느 컨테이너든 된다.

- 줄에 에이전트·우리 루프가 있으면 명령이 실행기의 `GET /health` 에 먼저 한 번 닿아 본다. 미리 보기는 그 결과를 한 줄
  찍는다(「실행기 agent-grader:8003 에 닿는다.」 또는 「… 에 닿지 못한다(URLError) — celery-worker 에서 돌린다」).
- 못 닿으면 `--confirm` 이어도 실험·칸을 하나도 만들지 않고 0 아닌 코드로 끝난다.

## 인프라 실패는 결과가 아니다

다음은 방식의 실패가 아니라 인프라 실패다 — 칸으로 남기지 않고, 같은 인자(같은 이름)로 다시 부르면 그 칸이 다시 돈다.

- 실행기에 닿지 못함·HTTP 오류(`AgentGraderError`), 동시 실행이 참(`AgentGraderBusy`)
- 실행 토큰 거절(`RunTokenRefused`, 실행 도중 프록시 401·403)
- 벤더 계정 쪽 거절(`AgentVendorRefused`)·실행 도중 하루 상한 429(`experiment_daily_limit`·`daily_limit`)

#1257 전에는 이런 칸도 `failed` 로 남았다. 그런 칸(`problem` 이 위 예외 이름으로 시작하는 `failed`)은 끝난 칸으로 세지
않고 보고표에도 넣지 않는다 — 다음 실행이 그 자리를 결과로 바꾼다. 데이터는 고치지 않는다.
모델이 답을 냈는데 틀린 꼴이거나 시간·실행 예산을 넘긴 것은 지금처럼 실패·보류 칸이고, 이것이 보고표의 실패율이다.
인프라 실패가 **연속 3칸**이면 거기서 멈추고 「남은 칸 N개」를 찍는다(0 아닌 코드).

## 돈은 따로 센다

- 에이전트·우리 루프는 실행 토큰 용도 `experiment` 로 `llm-proxy` 를 지난다. 프록시는 이 토큰을 운영 하루 상한
  (`AGENT_SCORING_DAILY_LIMIT_USD`)에 세지 않고 **실험 하루 상한 `AGENT_EXPERIMENT_DAILY_LIMIT_USD`** 에만 센다.
  넘으면 429 `experiment_daily_limit`.
- 한 번 호출은 벤더를 직접 부르므로 비용을 실험 표(`cost_usd`)에 적고 같은 하루 합계에 넣는다.
- **칸 예산**(#1259): 에이전트·우리 루프 칸 하나의 하드 상한은 $1 하나다 — 에이전트는 시도 둘(최초 + 재실행)을 합쳐서다.
  둘째 시도의 실행 토큰 예산은 칸 예산 − 첫 시도 지출이고, 남은 것이 없으면 재실행하지 않는다.
- 명령은 칸마다 먼저 「상한 − 오늘 쓴 돈 ≥ 이 줄의 칸당 최대」를 본다. 모자라면 거기서 멈춘다. 칸당 최대는 에이전트·우리
  루프면 **칸 예산**(실제로 끊기는 값)이고, 한 번 호출이면 높은 추정이다. 토큰 추정은 믿지 않는다 — 11-21 에 남은 $0.25 가
  추정 $0.18 보다 커서 시작한 칸이 $0.58 을 쓰다 끊겼다.
- 실행 토큰 예산은 min(칸 예산, 남은 하루 돈)으로 발급한다 — 하루 상한에 닿기 전에 토큰이 먼저 끊긴다.
- **넘칠 수 있는 것은 요청 하나다.** 프록시는 요청 **전에** 쓴 돈만 보고(응답이 끝나야 비용을 안다), 요청 하나의 최대
  비용은 입력 크기를 미리 몰라 셀 수 없다. 그래서 토큰 예산·하루 상한은 마지막 요청 하나 몫만큼 넘을 수 있다(시험이 이
  상한을 단언한다).
- 비용은 프록시가 **요청마다** 단가를 곱한 값이다(긴 프롬프트 할증은 요청 하나에 걸린다). 우리 루프 기록의 단계·요구사항별
  비용은 합계 usage 에 할증 없이 곱한 근사다(`cost_basis: sum_without_long_context`) — 11-21 전에는 합계에 Haiku 5.5 의
  10만 토큰 문턱을 걸어 칸 비용이 정확히 5배로 남았다.
- OpenAI 의 캐시 읽기(`cached_tokens`)는 단가표의 캐시 입력 단가로 센다(#1259 전에는 입력 정가로 셌다 — 4.1-mini 칸이
  2.5배쯤 부풀었다).
- **기본값 0 은 꺼짐이다** — 상한을 정하기 전에는 `--confirm` 을 줘도 한 칸도 돌지 않는다.

## 순서

먼저 **2건 × 1회**로 단가를 실측하고(대장 #4345), 보고표의 「전체 예상」을 사람이 본 뒤 같은 실험을 전체로 넓힌다.

1. **미리 보기** — `--confirm` 없이 부른다. 모델을 부르지 않고 실험 표도 만들지 않는다.

   ```bash
   docker compose -f docker/compose.prod.yaml exec celery-worker \
     python manage.py compare_scoring_methods --contest 3 --repeat 3 --limit-submissions 16
   ```

   찍는 것: 실험 이름, 제출 수 × 회차, 남은 칸, 줄마다 남은 칸·예상 비용 범위·칸당 최대, 합계, 실험 하루 상한·오늘 쓴 돈·남은 돈,
   그리고 뽑힌 제출마다 기대 점수(운영 점수 — 끝난 정정이 있으면 그 점수)와 미충족 수(필수, 선택·가산).
   **기대 점수가 모두 같으면 방식을 가를 수 없다**(#1261 — `contest3-four-s4` 는 16건 모두 100 이라 32칸·판정 704개가 전부
   100·충족이었다). 미리 보기가 그렇다고 한 줄 찍고, `--confirm` 은 한 칸도 만들지 않고 거절된다. 비용만 재는 것이 목적이면
   `--cost-only` 를 같이 준다 — 그 실험은 비용 측정 전용으로 남고 보고표 머리가 「비용 측정 전용 — 점수 비교 아님」을 찍는다.
   제출이 하나뿐이어도 같다고 본다. `--pick spread` 인데 공모전의 채점된 제출 점수가 모두 같으면 그것도 한 줄 찍는다(id 순과 같다).
   `--rows` 를 비우면 기본 줄 일곱이다 — 기준 `agent:claude-sonnet-5-5`, 그리고 `claude-haiku-5-5`·`gpt-4.1-mini` 마다
   `single_call`·`agent`·`self_loop`. 첫째 줄이 보고표의 기준 줄이다.
   예상 비용은 공모전 3 실측에서 잡은 토큰 범위 × 단가(에이전트·우리 루프는 낮은 쪽만 — 높은 쪽과 칸당 최대는 칸 예산 $1)이고, 같은 실험이
   이미 돈 칸이 있으면 그 줄의 실제 최소·최대로 바뀐다. 단가는 실제 비용과 같은 계산(`usage_cost_usd`)이다 — 한 번 호출의
   높은 쪽은 입력 300k 로, Haiku 5.5 의 10만 토큰 초과 5배 단가까지 넣어 공모전 3 실측(입력 100k~255k)을 덮는다.
2. **금액 확인** — 합계 예상의 높은 쪽을 보고 사람이 쓸 돈을 정한다.
3. **상한 설정** — 운영자 앱 「운영 설정」의 `AGENT_EXPERIMENT_DAILY_LIMIT_USD`(「기타」 묶음)에 그날 쓸 금액을 저장한다.
4. **단가 실측** — `--limit-submissions 2 --repeat 1 --name <이름> --confirm`(두 건의 점수가 같으면 `--cost-only` 도). 제출은 id 오름차순으로 앞의 2건이다.
   `--pick spread` 면 운영 점수 순으로 양 끝을 포함해 고르게 N 건이다(실험에 남아 이어 돌려도 고르는 법이 바뀌지 않는다 —
   다른 `--pick` 을 주면 거절한다. 이 선택지 전에 만든 실험은 id 순이다).
   보고표(`experiment_report <이름>`)의 「실측 건당 비용」과 「전체 예상」(실측 건당 비용 × 공모전의 채점된 제출 전부 × 회차 3)을
   보고 전체 실행 금액을 정한다. 회차 1 보고표의 흔들림은 「회차 1 — 잴 수 없음」이다.
5. **전체 실행** — 같은 `--name` 에 `--repeat 3`(건수 제한 없이) `--confirm`. 줄이 같으면 같은 실험이 넓어지고, 이미 돈
   2건 × 1회는 다시 돌지 않는다. 칸마다 한 줄(상태·점수·비용)을 찍는다.
6. **이어 가기** — 상한에 멈췄으면 「남은 칸 N개」가 찍힌다. 다음 날(또는 상한을 올린 뒤) **같은 인자로** 다시 부르면
   같은 실험(인자에서 만든 이름, 또는 `--name`)의 남은 칸만 돈다. 끝난 칸은 다시 돌지 않는다(방식의 실패 칸도 — 실패율이
   보고표의 숫자다). 인프라 실패 칸은 끝난 칸이 아니라 다시 돈다(위 절).
7. **끝나면 상한을 0 으로** 돌려 둔다.
8. **보고표** — `python manage.py experiment_report <실험 이름>`(마크다운), `--format csv`(CSV).
9. **청구 대조** — `python manage.py experiment_report <실험 이름> --bill`. 벤더·모델·UTC 날짜·UTC 한 시간 창마다 요청 수,
   입력, 캐시 읽기·쓰기, 출력, 금액을 찍는다 — 벤더 콘솔의 사용량(UTC)과 줄 단위로 맞춰 본다. 에이전트·우리 루프는 이 실험이
   만들어진 뒤 그 제출들에 발급된 실험 실행 토큰(프록시 합, 발급 시각 기준)이고, 결과로 남지 않은 인프라 실패 칸의 몫도 든다.
   한 번 호출은 칸 하나를 요청 하나로 센다. 같은 제출에 같은 때 다른 실험을 돌렸으면 섞인다. #1259 전에 기록된 OpenAI 금액은
   캐시 읽기를 입력 정가로 센 값이다.

## 사본 재료 — 운영 강의실 제출로 개발 환경에서 (#1262)

공모전 3 은 운영 제출 16건이 모두 100점이라 방식을 가르지 못했다(#1261). 그래서 운영 강의실 제출 가운데 점수가 갈리는 것을
가명 사본으로 꺼내 **work 개발 환경에서** 실험한다(대표 결정, 대장 #5025). 운영 서버에서는 실험을 돌리지 않는다.

1. **꺼내기(대장, 운영)** — 읽기만 한다. 화면에는 건수와 크기만 나온다.

   ```bash
   docker compose -f docker/compose.prod.yaml exec backend \
     python manage.py export_experiment_material --classroom-submissions <id,…> --name <이름> --out /tmp/<이름>.tar.gz
   ```

   담는 것: 운영 채점이 읽은 소스(저장소는 고정 커밋의 zip), 문제 제목·설명·채점 지침, 체크리스트 항목(id·라벨·등급·숨김·점수,
   가산 제외), 운영 판정(항목·충족·근거)과 model_version, manifest(가져온 날·이름·건수·체크섬). 이름·계정·멤버 id·이메일·
   클래스 이름·제출 시각·운영 제출 id·자산 라벨은 담지 않는다 — 제출은 가명 id(이름 솔트 + sha256 앞 12자)뿐이다.
   꺼낼 수 없는 제출(고정 커밋 없음·저장소가 GitHub 에서 닿지 않음)은 건너뛰고 끝에 `건너뜀 N건 — 까닭 n(제출 번호,…)` 한 줄을 찍는다. 꺼낸 건수가 0 이면 파일 없이 실패한다.
2. **옮기기** — work 의 `~/.cache/codemit-work/experiment-material/<이름>/` 로 scp 한다. **운영 서버에 남은 파일은 옮긴 뒤 지운다.**
3. **미리 보기(dev)** — `python manage.py compare_scoring_methods --material ~/.cache/codemit-work/experiment-material/<이름>/<이름>.tar.gz
   --repeat 1 [--rows …]`. 사본에서 입력을 짓는다 — 운영 DB·저장소·GitHub 를 부르지 않는다. 제출 칸은 가명 id 다. 기대 점수는
   사본의 운영 점수(필수 충족 비율)이고, 모두 같으면 `--confirm` 은 위 절처럼 거절된다. `--rows` 를 비우면 기본 줄 일곱에
   `classroom_call:gpt-4.1-mini` 를 더한 여덟이다. `classroom_call:<모델>` 은 강의실 운영 채점과 같은 프롬프트·한 번 호출이라
   「운영 판정(gpt-4.1-mini, 강사 키)」과 같은 길의 재현이다(사본에서만 받는다).
   `classroom_staged:<모델>`(#1295)은 같은 사본에서 staged 갈래를 돈다 — 기계 판정·인용 대조·의심 올림·두 걸음은 운영 설정 기본값대로, 같은
   입력 재사용은 끈다. `classroom_call` 줄과 한 사본·한 실험에서 나란히 돌려 정확도·비용을 비교한다. 보고표의 「기계 확정 항목 수」·「모델에 간 항목 수」는
   이 줄만 채운다. 도출 호출(#1293)은 아직 잇지 않았다(강사 규칙만).
   벤더 키(운영 설정 `OPEN_AI_API_KEY`·`ANTHROPIC_API_KEY` — dev 운영자 앱에 대장이 넣는다, 저장소에 값을 두지 않는다)가 빈 줄은
   「키 없음」으로 찍힌다.
4. **승인** — 미리 보기 금액을 보고 대표가 규모(건수 × 회차)를 정한다. 하루 상한·칸 예산은 위 절과 같다.
5. **실행** — 같은 인자에 `--name <실험>` `--confirm`. 키 없음 줄이 있으면 한 칸도 만들지 않고 거절한다. 이때만 이 명령의 직접 호출
   (`single_call`·`classroom_call`·`classroom_staged`)이 개발 환경 어댑터 모드(fake)와 상관없이 실험 키로 실제 벤더에 나간다 — dev 의 다른 곳은
   그대로 fake 다. 키 인증 실패(만료)는 인프라 실패라 결과로 굳지 않고 연속 3칸이면 멈춘다.
6. **보고** — `experiment_report <실험>`. 사본의 운영 판정이 「운영:<model_version>」 줄(돈 0)로 들어가고, 표 아래에 운영 점수
   구간(필수 충족 0~20·20~40·40~60·60~80·80~100%)별 「줄 − 운영」 평균 차가 붙는다.
7. **지우기** — `compare_scoring_methods --purge-material <이름>` 이 `~/.cache/codemit-work/experiment-material/<이름>/` 을 지운다.
   실험 표의 칸(가명 id·판정)은 dev DB 에 남는다.

사본 규칙: 저장소 밖에 둔다 — 저장소 안이나 `/tmp` 아래면 읽지 않는다. 읽을 때 파일을 0600, 폴더를 0700 으로 좁힌다.
manifest 의 가져온 날이 7일을 넘으면 미리 보기와 보고표가 경고한다. 체크섬이 manifest 와 다르면 읽지 않는다.

## 보고표가 말하는 것

줄마다: 제출·회차·채점·보류·실패 수, 기준 줄 대비 평균 점수 차(제출별 회차 평균끼리의 절댓값 평균)·최대 차, 순위 일치
(스피어만), 흔들림(제출별 회차 표준편차의 평균), 근거 실재율, 실측 건당 비용, 전체 예상(제출 N × 회차 3), p50·p90 시간.
돈이 든 칸이 하나도 없는 줄(인프라 실패만 있었다 등)의 전체 예상은 「실측 없음」이고 합계에서 빠진다 — 머리 줄이 몇 줄이
빠졌는지 말한다. 실험의 줄 가운데 남은 칸이 없는 줄도 빈 줄(회차 0)로 보인다.
그리고 문턱 여덟(스펙 #1244 넷 + 대장 #4345 설계안, 줄마다 통과·미달, 판단할 수 없으면 「—」):

| 문턱 | 통과 |
| --- | --- |
| 평균 차 | 기준 줄 대비 평균 점수 차 ≤ 5점 |
| 최대 차 | ≤ 15점 |
| 순위 일치 | 스피어만 ≥ 0.8 |
| 흔들림 | ≤ 기준 줄의 흔들림 + 2 |
| 근거 | 근거 실재율 ≥ 95% |
| 실패·보류 | (실패 + 보류) / 회차 ≤ 1/16 |
| 비용 | 실측 건당 비용 ≤ 기준 줄의 1/3 |
| 시간 | p90 ≤ 300초 |

요구사항 단위(#1261) — 점수가 같아도 판정은 다를 수 있다:

- **판정 일치율**(필수·선택): (제출, 요구사항)마다 이 줄의 회차 판정과 기준 줄의 회차 판정을 모든 짝으로 견준 일치 몫의
  평균. 선택에는 가산이 든다. 기준 줄 자신은 「—」.
- **판정 흔들림**(필수·선택): 채점된 회차가 둘 이상인 (제출, 요구사항) 가운데 회차마다 판정이 바뀐 몫. 회차 1 이면 「—」.
- **기준 판정과의 일치·기준 미충족 재현율·기준 대비 오탐률**(#1288): 항목별 기준 판정이 있어야 잰다. 일치 = 기준 판정과 판정이 같은 칸(제출 × 항목 × 회차)의
  몫, 재현율 = 기준이 미충족인 칸 가운데 미충족으로 판정한 몫, 오탐률 = 기준이 충족인 칸 가운데 미충족으로 판정한 몫. 기준 판정이 없는
  재료는 「—」이고 머리에 그 말이 붙는다(결함을 심은 변형 제출은 대표 지시로 하지 않았다, 대장 #5023). **정답 채우기**: 가명 id·항목 id·
  충족 여부 세 열의 CSV(`material_id,item_id,is_met` — 충족·미충족·true·false) 를
  `python manage.py compare_scoring_methods --material <사본> --fill-truth <정답.csv>` 로 사본에 채운다(모델을 부르지 않는다). 모르는
  제출 id·그 제출에 없는 항목 id·값을 못 읽는 칸·같은 칸 둘·CSV 에 나온 제출의 빠진 항목은 거절하고 사본은 그대로다. 원문·학생 정보는 받지
  않는다. 정답이 채워진 사본으로 `--confirm` 하면 「정답:사람」 줄(돈 0)로 남아 보고표가 줄로 세지 않고 기준으로만 쓴다. 정답을 누가 매길지는
  대표 결정 대기다.

문턱 둘이 더 있다(위 여덟과 합쳐 열):

| 문턱 | 통과 |
| --- | --- |
| 필수 일치 | 필수 판정 일치율 ≥ 95% — 평균 차 5점을 판정 수로 옮겼다(필수 14개면 하나가 7.1점, 5점 ≈ 필수의 5%) |
| 필수 판정 흔들림 | ≤ 기준 줄의 필수 판정 흔들림 + 2%p — 점수 흔들림 슬랙 2점을 같은 식으로 옮겼다 |

근거 실재율은 모델이 낸 `경로:줄` 을 박제본에서 우리 루프와 같은 검사(`selfloop.check_evidence`)로 확인한 몫이다. 우리
루프는 확인하지 못한 근거를 판정에 남기지 않으므로, 다시 물어 버린 근거(`evidence_dropped`)를 분모에 넣는다. 한 번
호출은 근거를 `경로:줄` 로 내지 않아 「—」다. 머리에는 표본 수와 한계(평균 차의 95% 신뢰 구간 반폭, 회차·제출이 적을 때의
경고)가 붙는다.

## 표본을 늘리는 길 (제안 — 결정 아님)

- 공모전 하나의 제출은 수십 건이라 평균 차 ±5점을 가르기 어렵다. 끝난 공모전 여럿을 같은 줄로 돌려 보고표를 합치는
  `--contest` 여러 개 받기.
- 운영 채점 대기와 겹치지 않는 시간대에 날마다 상한만큼 이어 돌리는 예약 실행.
- 사람이 매긴 점수(이의 심사 결과)가 있는 제출을 따로 묶어, 기준 줄 대신 사람 점수와 견주는 줄.
